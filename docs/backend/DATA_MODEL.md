## 2. Conventions

- **IDs: UUID** primary keys for every externally visible resource, generated by the application with the standard library's `uuid.uuid4()` and stored as native Postgres `uuid`. _Why:_ non-guessable, safe to expose in URLs (`/businesses/:id`), mergeable across environments (fixtures, staging→prod), no enumeration of competitors' listing counts, compatible with the frontend's opaque-string ids. _Trade-off:_ 16 bytes vs 8, and random v4 values have poorer B-tree locality than time-ordered ones — acceptable at B-17's scale; bigint PKs were rejected because they leak counts/order and would force a second public identifier. Time-ordered UUIDv7 was an optional preference ("where available"), not a requirement, and is **not** used: no custom generator and no extra dependency. Switching later is an application-only change (the column type does not change). One strategy everywhere; no mixing. Reference/lookup tables that are code-defined stay as enum/text, not rows.
- **Time:** `timestamptz`, UTC, `created_at`/`updated_at` on mutable tables (set by the app/DB, not clients). News `published_at` is a `date`.
- **Naming:** snake_case tables/columns, plural table names, FKs `<thing>_id`. Constraints and indexes get explicit conventional names (naming convention in `db/`).
- **Strings:** length limits come from the current frontend schemas and are mirrored as `varchar(n)`/CHECKs where they are domain rules.
- **Enums:** `VARCHAR(32)` + a named `CHECK` (decided in 10C; not native PostgreSQL enums — changing a CHECK is a reversible migration, `ALTER TYPE … ADD VALUE` is not); Python gets `StrEnum` types.
- **Ownership of rules:** the DB guarantees what it cheaply can; services own the rest (marked _service rule_).

## 4. Listing architecture — base table + subtype tables

```mermaid
flowchart TB
  L["listings (base)<br/>id · kind · owner_id · status · title · description · area · tags · image · is_featured · revision · submitted_at"]
  L -->|"kind=business"| B["business_profiles<br/>vertical: general | food"]
  B -->|"vertical=food"| F["food_profiles<br/>service_options · hours_note · menu_image"]
  F --> M["food_menu_items (≤ 8)"]
  L -->|"kind=property"| P["property_profiles<br/>listing_type · price_text · bedrooms · furnished"]
  L -->|"kind=tutor"| T["tutor_profiles<br/>grade"]
  L -->|"kind=provider"| X["(no subtype table in V1)"]
```

**Strategy: class-table inheritance with shared primary key.** `listings` holds everything every kind shares _and_ everything the lifecycle needs (owner, status, history, quota, moderation, Saved, search). A subtype table's PK **is** its `listing_id` (FK, `ON DELETE CASCADE`).

|                                   | Pros                                                                                                                                                                               | Cons                                                                                                                                                                                                                        |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Chosen: base + subtype tables** | One lifecycle, one owner/quota rule, one Saved/moderation/search path for all kinds; subtype columns are real, typed, constrained; adding a kind = one table, not a new lifecycle. | Reads of a full listing join base + subtype (cheap, PK joins); creation touches two tables (one transaction).                                                                                                               |
| One giant `listings` table        | No joins.                                                                                                                                                                          | Hundreds of nullable columns, no meaningful NOT NULL/CHECKs, every new kind widens the hot table. **Rejected.**                                                                                                             |
| JSONB blob for kind data          | Flexible.                                                                                                                                                                          | No constraints/typing/indexing of the fields the filters use (`bedrooms`, `listing_type`, `vertical`); validation only in app code. **Rejected** for domain fields (JSONB stays available for genuinely schemaless extras). |
| Fully separate tables per kind    | Simple per kind.                                                                                                                                                                   | Duplicated lifecycle/status/history/Saved/quota — the duplication the frontend deliberately avoided. **Rejected.**                                                                                                          |

`kind` is immutable after creation (changing a listing's kind is a new listing). A `listings.kind` ↔ subtype-row match is **enforced by the database** (composite FK `(listing_id, kind) → listings(id, kind)` + `CHECK kind = '<kind>'` on each subtype — §14); `owner`, `status` and `revision` are enforced in services and guarded updates (`BACKEND_ARCHITECTURE.md` §6).

### 4.1 `listings`

`id uuid PK` · `kind` (enum, NOT NULL) · `owner_id uuid NULL → users` (NULL = admin-curated/unclaimed seed content) · `status` (`pending|approved|rejected|archived`, NOT NULL) · `title varchar(100)` NOT NULL · `description text` · `area text` NOT NULL · `tags text[]` NOT NULL DEFAULT `{}` · `image_url text` (interim, §1) · `is_featured bool` DEFAULT false · `revision int` NOT NULL DEFAULT 1 (the **integer concurrency/version counter** — a current requirement; incremented on every content edit; see _Revision counter vs revision history_ in §7) · `submitted_at timestamptz` NOT NULL · `search_document text` NOT NULL DEFAULT `''` (denormalized lower-cased public text — **added in Phase 10D by migration `0002`** together with its maintenance, §9 and §14.1) · `created_at`, `updated_at`.

CHECKs: `tags` normalized by the service (lowercase/trim) and `array_length` sane; `title` non-blank; `is_featured` only for kinds that have it (`CHECK featured_kinds`: provider/business). Per-kind **length limits** differ (name ≤80 vs property title ≤100) — enforced by per-kind create schemas; the column takes the max.

### 4.2 `business_profiles`, `food_profiles`, `food_menu_items`

- `business_profiles(listing_id PK/FK, vertical NOT NULL DEFAULT 'general', UNIQUE(listing_id, vertical))`.
- `food_profiles(listing_id PK, vertical NOT NULL DEFAULT 'food' CHECK (vertical='food'), service_options text[] NOT NULL CHECK (cardinality ≥ 1 AND <@ {dine-in,takeaway,delivery}), hours_note varchar(80), menu_image_url, FOREIGN KEY (listing_id, vertical) → business_profiles(listing_id, vertical))`. The composite FK makes it **impossible** for a Food profile to exist on a non-food business. The converse (a `vertical='food'` business _must_ have a `food_profiles` row and ≥1 Food category) is a _service rule_, written in the same transaction.
- `food_menu_items(id uuid PK, listing_id FK→food_profiles, position smallint CHECK 1..8, name varchar(60) NOT NULL, section varchar(40), description varchar(120), price_text varchar(24), UNIQUE(listing_id, position))` — the DB itself caps highlights at 8.

### 4.3 `property_profiles`, `tutor_profiles`

- `property_profiles(listing_id PK/FK, listing_type enum(sale|rent) NOT NULL, price_text varchar NOT NULL, bedrooms smallint CHECK ≥0, furnished enum(Furnished|Unfurnished|Semi-Furnished))`. `property_type` lives in `listing_categories` (module `property`).
- `tutor_profiles(listing_id PK/FK, grade text NOT NULL)`; subject = primary category (module `education`).

## 5. Food mapping (preserves current Food behavior)

| Frontend behavior                                                                  | Persistence                                                                                                                                                                                             |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Listing kind `business`, vertical `food`                                           | `listings.kind='business'` + `business_profiles.vertical='food'` + `food_profiles` row                                                                                                                  |
| 1–3 categories, first is primary _(a **Food** rule)_                               | `listing_categories` rows with `position` 1..n, **primary = position 1**; the maximum of 3 is enforced by the Food service, not by the generic table                                                    |
| `Business.category` derived from primary                                           | Read-model: name of the position-1 category. Never stored separately.                                                                                                                                   |
| Canonical slugs (`bakeries`, `desi-food`, …)                                       | `categories` rows (module `food`), seeded from `config/food.ts`; slugs are the stable ids                                                                                                               |
| ≥1 service option, canonical order                                                 | `food_profiles.service_options` (the API returns canonical order)                                                                                                                                       |
| ≤80 hours text; ≤8 menu highlights with display-string prices; optional menu image | `hours_note`; `food_menu_items` (cap by CHECK); `menu_image_url`                                                                                                                                        |
| Search: `type=business&vertical=food&foodCategory=<slug>&service=<opt>`            | `business_profiles.vertical`, a `listing_categories`→`categories` join, `service_options @> ARRAY[…]`                                                                                                   |
| Edit → prefill → resubmit never drops Food data                                    | Edit = replace categories + menu items inside the edit transaction; `food_profiles` row kept                                                                                                            |
| Switching a Food business to General                                               | A _service rule_: deletes the `food_profiles`, menu items and Food categories, assigns a General category, flips `vertical` — in one transaction (the frontend warns that Food data is removed on save) |

**Categories: why `position` instead of an `is_primary` flag.** Primary-by-position is the frontend's own rule ("the first is primary") and removes a second field that could disagree with the order. `UNIQUE(listing_id, position)` + `CHECK (position >= 1)` give the generic relation uniqueness and a sane lower bound; **the "at most 3" cap is Food-specific** (docs/product/FOOD_DINING.md) and every other kind has exactly one category, so the shared table deliberately carries no maximum — the Food service enforces 1..3, contiguous positions from 1 (so a primary exists) and the module match, and verifies them again by reading the stored rows back inside the transaction (a violation rolls everything back). No trigger. The alternative — `is_primary` + a partial unique index — was rejected for the redundancy; revisit only if categories ever need an order independent of primacy.

## 6. Other tables

**`professional_profiles`** — `user_id PK/FK`, `plan_code` (`free|premium`, DEFAULT `free`), `created_at/updated_at`; future `verification_status`. Exists because plan/entitlements and (later) verification belong to the _professional_ concept, not every account. Created when a user first uses the professional workspace (the frontend lets any signed-in user list — no admin approval to become a professional). It is also the **row locked during quota-checked creates**.

**`saved_items`** — `PRIMARY KEY (user_id, listing_id)`, `created_at`. **One table for all kinds** (kind derived via the listing). Behavior: only approved (publicly visible) listings can be saved; if the listing later becomes non-public (pending after an edit, rejected, archived) the row is **kept** but hidden from the Saved list — mirroring the frontend, which filters unresolvable references — and reappears if re-approved. Hard-deleting a listing cascades. News is not saveable (as today).

**`news_articles`** — `id`, `kind` (`news|update`), `status` (`draft|published`), `title` ≤120, `summary` ≤400, `category_id → categories` (module `news`), `image_url`, `published_at date`, `tags text[]`, `created_by → users`, `created_at/updated_at`. Public reads require `status='published'`. No moderation lifecycle (admin-authored), so it does not use `listing_status_history`.

**`service_requests`** _(conceptual in 10A)_ — `id`, `requester_id → users`, `provider_listing_id → listings` (kind provider), `provider_name_snapshot`, `service`, `details` (10–500), `area`, `preferred_date date`, `preferred_time`, `notes`, `status` (`submitted|accepted|in-progress|completed|cancelled`), timestamps; transitions = `REQUEST_TRANSITIONS` (terminal: completed, cancelled), with a small status-history table when that phase is built. Visible to the requester and to the listing's owner. A contact channel is **not** modelled (O-3).

## 7. Listing lifecycle (state machine) and history

Statuses: `pending`, `approved`, `rejected`, `archived`. There is **no `draft`** today (the form is submit-only); `draft` is reserved as an additive future value together with a `POST …/submit` action.

| #   | Actor | From → To                                    | Action        | Source                                    | Rules                                                                                                                                                                                                                                                     |
| --- | ----- | -------------------------------------------- | ------------- | ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Owner | ∅ → `pending`                                | `submitted`   | `ListingFormPage.submitListing`           | Quota check (active = pending+approved < plan max); creates subtype/categories; history row.                                                                                                                                                              |
| 2   | Owner | `pending`/`approved`/`rejected` → `pending`  | `resubmitted` | `EditListingPage.resubmitListing`         | Content replaced; `revision`++; `submitted_at` reset; current rejection reason ceases to apply. **An edit takes an approved listing offline until re-approved** (frontend: "it won't stay public while changes are pending"). `archived` is not editable. |
| 3   | Admin | `pending` → `approved`                       | `approved`    | `ReviewPanel.handleApprove`               | Must carry the reviewed `revision`; becomes publicly visible.                                                                                                                                                                                             |
| 4   | Admin | `pending` → `rejected`                       | `rejected`    | `ReviewPanel.handleConfirmReject`         | **Reason required, ≥10 chars** (CHECK on history).                                                                                                                                                                                                        |
| 5   | Admin | `approved` → `rejected`                      | `rejected`    | UI allows rejecting any status            | Takedown with required reason — kept because the frontend does it; confirm in Phase 12 (O-5).                                                                                                                                                             |
| 6   | Owner | `pending`/`approved`/`rejected` → `archived` | `archived`    | `ProfessionalListingsPage.archiveListing` | Terminal in V1.                                                                                                                                                                                                                                           |

**Everything else is rejected** with `409 invalid_state_transition`: e.g. admin approving a `rejected` (owner must edit and resubmit) or `archived` listing — the **frontend UI currently lets an admin click Approve/Reject on any status, including archived (a latent looseness); the backend is deliberately stricter** — and archived → anything (no unarchive in V1; reserved).

**Quota:** active = `pending`+`approved`. Rejected/archived free a slot (frontend rule, `isListingCountedTowardPlanLimit`).

**Visibility:** public reads return `status='approved'` only (news: `published`). Owners additionally see their own listings in every status; admins see all. This predicate lives in **one** repository helper (the frontend's `approvedListings()` equivalent).

### Revision counter vs revision history (do not conflate)

- **Current requirement — `listings.revision`:** a simple integer counter on the listing row. It increments on every content edit and is compared in guarded updates so a **stale moderation decision or a conflicting update is rejected** (`409`). It stores no content.
- **Deferred — content-version history:** full snapshots of a listing's past content (who changed which fields, restoring or diffing versions, keeping an old approved version live while a new one is reviewed), e.g. a future `listing_revisions` table. Not part of V1.
- **Unchanged — status history:** `listing_status_history` below remains append-only and records lifecycle transitions only (it also stores the `revision` the transition applied to).

### `listing_status_history` (append-only audit)

`id`, `listing_id → listings` (cascade), `from_status` (NULL for creation), `to_status`, `action` (`submitted|resubmitted|approved|rejected|archived`), `revision int`, `actor_user_id → users`, `actor_role`, `reason text` (CHECK: required when `to_status='rejected'`), `created_at`.

- **Creation is recorded** (`from NULL → pending`, action `submitted`) so the history is complete and the "pending" starting point and time are auditable.
- **Resubmissions are recorded even when `pending → pending`** — hence the `action` column in addition to from/to (the brief's minimal `previous/new status` cannot distinguish a resubmission from nothing).
- Written in the **same transaction** as the status change; never updated or deleted by the application.
- **Single source of truth for the rejection reason:** the _current_ reason is derived from the latest `rejected` history row while the listing is `rejected` (no separate `rejection_reason` column to drift).

## 8. Dynamic categories (taxonomy)

**Requirement:** production categories must not require frontend code changes. Today they are hard-coded (service categories in `data/serviceCategories.ts`, Food in `config/food.ts`, Property types in a `<select>`, General-business category as free text, News category as free text, Education subject as seed text).

**`categories`** — `id uuid`, `module` (`services|directory|food|education|property|news`; a **code-defined** enum stored as text+CHECK), `name`, `slug`, `parent_id → categories NULL` (hierarchy is **supported but not required**; Food and Services are flat today), `is_active bool` DEFAULT true, `display_order int` DEFAULT 0, `created_at/updated_at`.
Constraints: `UNIQUE(module, slug)`; `parent_id` must belong to the same module (composite FK `(parent_id, module)`, database-enforced); `slug` format CHECK; slugs of seeded categories equal the current frontend slugs (`bakeries`, `construction`, …) so URLs and filters stay stable.

**Rule: a _category_ is the primary classification a user browses/filters by inside an existing module** — Services category, Directory category, Food category, Property type, Education subject, News category. Everything else (`vertical`, `listing_type`, `furnished`, `bedrooms`, `grade`, service options) is an _attribute_, not a category.

**A category is not a module.** An admin can add _"Used Mobiles"_ under an **existing** taxonomy later, but a new top-level capability (Marketplace, Pharmacy…) needs product architecture: new routes, a subtype table, lifecycle rules, search integration. `module` is therefore a code-defined enum; adding one is a code + migration change, never an admin action.

**How categories feed the product later:** (1) _listing forms_ load active categories for the listing's module (`GET /categories?module=…`) instead of constants; (2) _Search filters_ build their options from the same endpoint (replacing `getCategoryOptions` derived from data); (3) _discovery pages_ (Food landing tiles, Services grid) render from it; (4) _Admin_ CRUD for create/edit/activate/reorder (Phase 12+). Icons stay a frontend presentation concern keyed by slug (an optional `icon_key` may be added later).

**Deactivation (`is_active=false`)** hides a category from pickers and filter option lists but never breaks existing listings: they keep the link and display it. A category in use cannot be deleted (`ON DELETE RESTRICT`).

**`listing_categories`** — `(listing_id, category_id, position)`; `UNIQUE(listing_id, category_id)`, `UNIQUE(listing_id, position)`, `CHECK(position >= 1)`; PK `(listing_id, position)`. It is a **generic** relation shared by every listing kind, so it carries **no maximum**. Per-module cardinality (Food 1–3; every other listing exactly 1; `vertical=food` ⇒ module `food`, `general` ⇒ `directory`) and contiguous positions are _service rules_ (a cross-row/type-specific check is not expressible as a row CHECK without triggers). _(The Phase 10A draft wrote `CHECK(position BETWEEN 1 AND 3)` here; that encoded Food's limit on the shared table and was corrected in 10C before the migration was published.)_

## 9. Search and indexing direction (database part; HTTP part is in API_CONTRACT)

The frontend's search is a **case-insensitive substring match** over `title + subtitle + description + area + tags (+ Food category labels + menu item names)` plus exact-match filters; there is **no ranking** for results (insertion order; only _suggestions_ are ranked). PostgreSQL reproduces that faithfully:

1. **V1 — maintained `listings.search_document`** _(created in Phase 10D with the service that keeps it correct; see §14.1)_: (lowercased concatenation of those fields incl. category names and Food menu item names), rebuilt by the service in the write transaction, with a **`pg_trgm` GIN index** so `search_document ILIKE '%q%'` is index-assisted. Exact filters use B-tree/GIN indexes.
2. **Later, only if evidence demands:** Postgres full-text search (`tsvector`, ranking, stemming) and/or trigram similarity for typo tolerance; **PostGIS** for distance; and only at real scale a dedicated engine. No Elasticsearch/OpenSearch now.

Indicative indexes (final in 10C, driven by `EXPLAIN` on real queries): `listings(status, kind, created_at)`, `listings(owner_id, status)`, `listings` GIN(`tags`), GIN(`search_document gin_trgm_ops`), `listing_categories(category_id, listing_id)`, `categories(module, is_active, display_order)`, `food_profiles` GIN(`service_options`), `property_profiles(listing_type)`, `saved_items(user_id, created_at DESC)`, `listing_status_history(listing_id, created_at)`, `news_articles(status, published_at DESC)`, `service_requests(provider_listing_id, status)` and `(requester_id, created_at DESC)`, unique index on `lower(users.email)`.

## 11. Constraints, delete/archive and deletion policy

**Database guarantees (in addition to application validation):** PKs/FKs everywhere with explicit `ON DELETE` (subtype/menu/categories/history/saved cascade from their listing; `listings.owner_id` and `categories` are not cascaded) · `UNIQUE(categories.module, slug)` · `UNIQUE(saved_items.user_id, listing_id)` · `UNIQUE(lower(email))` · `UNIQUE(provider, provider_subject)` on identities · NOT NULL where the domain requires it (`status`, `kind`, `title`, `area`, `submitted_at`, `service_options`) · CHECKs (≤8 menu items by `position`, ≤3 categories by `position`, `bedrooms ≥ 0`, enum domains, `reason` required on rejection, lengths) · composite FK tying `food_profiles` to a food-vertical business · timestamps on every mutable table · partial indexes where they remove scans (e.g. active listings per owner).

**Policy (no universal `deleted_at`):**

- **Business archive** (`status='archived'`) is a lifecycle state of a listing: reversible in the domain's future, hidden from public reads, still owned, still in history. It is _not_ deletion.
- **Hard delete of a listing** is an exceptional admin/ops action (e.g. legal removal) — cascades its subtype/menu/categories/Saved/history. Not exposed to owners.
- **Account deletion** is not a row delete: the `users` row becomes a tombstone (`status='deleted'`, PII scrubbed, identities and roles removed, sessions revoked); the user's listings are archived; Saved rows are removed; history keeps the `actor_user_id` (a non-PII tombstone). Detailed in Phase 11. _(RBAC freeze, 2026-11-19: a tombstone that would remove the last active, usable Super Admin is to be refused transactionally — `AUTH_RBAC.md` §27.6; planned.)_
- **Category deactivation** — see §8. **News**: `draft`/`published` is its own state; deletion by admin is a hard delete (no audit requirement yet).

## 14. Implementation notes (Phase 10C — the schema as built)

Source: `backend/app/models/` and `backend/alembic/versions/0001_initial_schema.py` (15 tables, verified on PostgreSQL 17). Where implementation refined the design above, the refinement is listed here and is binding. Nothing was redesigned: every item is an _additional_ database guarantee, a naming detail, or a deferral.

**Conventions as built.** Primary keys are application-generated UUIDs (`uuid.uuid4()` from the standard library; native `uuid` columns); development/test fixtures use name-based UUIDv5 and must never be used for real data. Every timestamp is `timestamptz`: `created_at` is database-generated (`now()`, the transaction's start time), `updated_at` is database-generated on insert and refreshed by the ORM on update (no trigger). Constrained values are `VARCHAR(32)` + a named `CHECK` — not native PostgreSQL enums (§2); Python code still gets `StrEnum` types. Constraints and indexes follow `pk_ / fk_ / uq_ / ck_ / ix_` naming, enforced by a test.

**Refinements to §1–§11**

1. **Subtype ↔ kind is database-enforced** (§4 said "service rule"): each subtype table has a `kind` column with `CHECK (kind = '<its kind>')` and a composite foreign key `(listing_id, kind) → listings(id, kind)`. A `business_profiles` row cannot exist for a property listing, and so on — the same mechanism the approved Food design uses.
2. **A category's parent must be in the same module** (§8 "service rule / composite FK"): implemented as the composite FK `(parent_id, module) → categories(id, module)`, plus `CHECK parent_id <> id`.
3. **A news article can only use a `news`-module category**: `category_module` (`CHECK = 'news'`) with the composite FK `(category_id, category_module) → categories(id, module)`.
4. **`is_featured` is row-checked** (§4.1 "service rule"): `CHECK (NOT is_featured OR kind IN ('provider','business'))`.
5. **`listing_status_history`** — `actor_user_id` is `NOT NULL` (`ON DELETE RESTRICT`; users are tombstoned, so the audit trail always has a valid actor); `actor_role` is `owner | admin`; row-local CHECKs: `from_status IS NULL` ⇔ `action = 'submitted'`; `to_status` is determined by `action` (`CASE`); a rejection needs a reason of at least 10 characters. The _allowed source status of each transition_ stays a service rule — no trigger. **`created_at` (Phase 12I):** the schema default stays `now()`, but the ORM supplies `clock_timestamp()` on every application INSERT, so each event carries the wall clock of ITS write (not the transaction start) and history is time-ordered even within one transaction — the same rule as `service_request_status_history`; no migration.
6. **`auth_identities.provider_subject`** is the column name (OIDC `sub`), not `provider_user_id`; unique together with `provider`. Nothing links identities by e-mail.
7. **`news_articles.created_by`** is nullable with `ON DELETE SET NULL` (authorship survives an account being removed).
8. **`listing_categories`** primary key is `(listing_id, position)`, plus `UNIQUE(listing_id, category_id)` and `CHECK position >= 1` (primary = position 1). **No maximum on the generic table**: Food's 1..3 is a service rule (see §8), so a Provider, Property or future kind is never limited by it.
9. **Deferred (not in `0001`):** `listings.search_document` and the `pg_trgm` extension — they shipped in Phase 10D (migration `0002`, §14.1) together with the service that _maintains_ the document (a denormalized column nothing keeps correct is worse than none); `GIN(tags)` is still not created; `service_requests` (conceptual in §6) and `media_assets` (reserved); `listing_revisions` (content-version history); a `provider_profiles` table.

**What PostgreSQL guarantees vs what a service must**

Fake users and demo listings (`python -m scripts.dev_fixtures`, name-based UUIDv5 ids) exist only for development/test/staging and the loader refuses `ENVIRONMENT=production`. _(RBAC freeze, 2026-11-19: the loader is planned to refuse `staging` as well — `AUTH_RBAC.md` §27.14; today it refuses only `production`.)_

### 14.1 Search foundation (Phase 10D — migration `0002_search_foundation`)

Real decisions only; the migration (`backend/alembic/versions/0002_search_foundation.py`) never touches `0001`.

1. **`pg_trgm`** is created (`CREATE EXTENSION IF NOT EXISTS`; trusted since PostgreSQL 13, present in the official image). The downgrade drops it. No other extension (PostGIS, unaccent, …) is installed.
2. **`listings.search_document text NOT NULL DEFAULT ''`** — the lower-cased, whitespace-collapsed public text a listing is found by: title, category names (position order), description, area, tags; Food menu-item names; property price text, "N bed", furnishing, "for sale"/"for rent"; tutor grade. Never owner/account data, moderation reasons, history, ids or status. Built by one pure function (`app/services/search_document.py`).
3. **Maintenance is application-level, not a trigger or generated column** (a document spans several tables, and 10C chose services + constraints over trigger meshes). The single entry point is `SearchIndexer` (`app/services/search_index.py`): `ListingCreationService` calls it **in the creation transaction**; any future code that changes a listing's content, menu, categories or a category's name must do the same. `find_stale()` recomputes every document and reports differences (used by tests and `python -m app.db.search_index check`); `rebuild_all()` repairs everything (`… rebuild`) and is the **required release step after `0002`** on any populated database (`alembic upgrade head` → `python -m app.db.search_index rebuild` → `… check`; `DEPLOYMENT.md` §4.1), which leaves existing rows with `''`. Never run automatically on startup. Proven by `tests/db/test_search_upgrade_path.py`.
4. **Indexes:** `ix_listings_search_document_trgm` — GIN `gin_trgm_ops` on `search_document` (serves `LIKE '%q%'`); `ix_listings_approved_area` — partial B-tree on `area WHERE status = 'approved'` (the public area filter). Existing indexes (`status/kind/created_at`, `news_articles(status, published_at DESC)`, category and profile indexes) serve the rest; `GIN(tags)` was **not** added — tags are searched through `search_document`, and the evidence (`EXPLAIN`, tests) shows no query that needs it yet.
5. **News has no stored document** (small, admin-authored): title, category name, summary and tags are matched in the query.
6. **Public visibility is query logic, not a view or RLS**: `status = 'approved'` (listings) / `'published'` (news) in every public query.

## 15. Authentication schema (Phase 11A design — **`0003` implemented in Phase 11B, `0004` in Phase 11C**)

Migration `0003_auth_sessions_tokens_events_rate_limits` exists and is applied (the `users` CHECKs and the four tables below); `0004_oauth_flows` (`oauth_flows`, `UNIQUE(user_id, provider)`) is the Phase 11C migration and is applied on top. `0001`–`0003` are never edited. Full rationale: [`AUTH_RBAC.md`](AUTH_RBAC.md) §3, §4.2, §8, §10, §13, §16.

**Audit of the existing identity tables — sufficient in shape:** `users` already has `email` (unique on `lower(email)`), `email_verified_at`, `display_name`, nullable `password_hash` (a social-only account has none), `status` (`active|suspended|deleted`) and `last_login_at`; `user_roles` (`admin` only; Resident is every account, Professional is a `professional_profiles` row); `auth_identities` (`provider_subject` is the stable key, `UNIQUE(provider, provider_subject)`); `professional_profiles`. **Decisions:** the password hash stays on `users` (one password per account; no credentials table); no username column; no new `users` columns; account status needs no schema change.

| `0003` (11B)              | `users`: `CHECK (email = lower(btrim(email)))`, `CHECK (char_length(email) <= 254)` · **`auth_sessions`** (`id`, `user_id`, `token_hash bytea` UNIQUE, `created_at`, `last_seen_at`, `expires_at`, `absolute_expires_at`, `revoked_at`, `revoke_reason`, `user_agent`) · **`auth_tokens`** (`id`, `user_id`, `purpose` `email_verification | password_reset`, `token_hash bytea`UNIQUE,`email`, `expires_at`, `consumed_at`, `created_at`) · **`auth_events`** (audit: `occurred_at`, `user_id`SET NULL,`actor_user_id`, `event_type`, `request_id`, allow-listed `details` JSONB) · **`auth_rate_limits`** (`key_hash`, `policy`, `window_start`, `count`) |

As built: `auth_sessions.token_hash`/`auth_tokens.token_hash` are `bytea` with `CHECK octet_length = 32` and a unique index; `auth_sessions` also has `CHECK (revoked_at IS NULL) = (revoke_reason IS NULL)`, `CHECK expires_at <= absolute_expires_at`, a partial index on `(user_id) WHERE revoked_at IS NULL` and an index on `expires_at`; `auth_events.request_id` is `varchar(64)` and `details` is JSONB (SQL `NULL` when empty, must be an object); `auth_rate_limits` has composite primary key `(key_hash, policy, window_start)`; every timestamp is written by the application clock. The `users` CHECKs are `ck_users_email_normalized` and `ck_users_email_length`.

`oauth_flows` (as built): both hashes are `bytea` with `CHECK octet_length = 32` and the `state_hash` has a unique index (`uq_oauth_flows_state_hash`); `CHECK ((purpose = 'link') = (user_id IS NOT NULL))`; `CHECK left(return_to, 1) = '/'`; `CHECK expires_at > created_at`; `provider`/`purpose` are `VARCHAR + CHECK` closed sets; an index on `expires_at` serves the sweep. It holds **no** provider token, authorization code or raw `state`/cookie secret — only hashes plus the short-lived `nonce` and PKCE `code_verifier` that must be readable to finish the round trip (single use, 10 minutes). The `0004` upgrade fails loudly (rather than deleting anything) if existing data has two identities of one provider for one user; it adds no data. Downgrade drops the table and the constraint.

Raw session and token secrets are **never stored** — only their SHA-256. Closed sets use `VARCHAR + CHECK`; all timestamps `timestamptz`; constraint names follow the existing convention. Expired rows are removed by `python -m app.cli.auth_maintenance purge` and are never trusted for correctness (validity is always checked against the timestamps).

## 17. Staff authority schema — **`0007` implemented in RBAC-A**; the rest of the RBAC-0 design is PROPOSED

**Status.** RBAC-0 (2026-11-19) created no migration, table, column or constraint; **RBAC-A then implemented the schema below as migration `0007_staff_authority`** (what was built, and where it differs from the proposal, is in _As built_). Everything not marked built — provider ownership (RBAC-D), the writers of most audit actions, and any later change — is still a proposal. The product decisions are frozen in [`AUTH_RBAC.md`](AUTH_RBAC.md) §27 and the implementation notes are its §28.

**As built (RBAC-A, `0007`):** `user_roles.role` is `admin | moderator`; `listing_status_history.actor_role` is `owner | admin | moderator`; `staff_scope_assignments` (primary key `(user_id, scope)`, constant `role = 'moderator'` with the composite foreign key `(user_id, role) → user_roles` `ON DELETE CASCADE`, `scope` the closed `CategoryModule` set, `granted_by` `SET NULL`, `granted_at`, an index on `scope`); `staff_audit_events` (columns and CHECKs as below, **no foreign keys**, four indexes); partial unique index `uq_user_roles_one_staff_role ON user_roles(user_id) WHERE role IN ('admin', 'moderator')` (a user cannot hold `admin` and `moderator` — a native invariant that holds under every transaction isolation level); row-level trigger `trg_staff_audit_events_append_only` (UPDATE / DELETE refused) and statement-level trigger `trg_staff_audit_events_no_truncate` (TRUNCATE refused), both sharing one function. `downgrade` refuses while any moderator role, scope assignment, staff audit event or `moderator` listing decision exists, and uses `DROP ... IF EXISTS` for the audit triggers and the exclusivity index so a deliberate operator cleanup that removed them first does not fail. The proposal's open questions were settled as: the exclusivity backstop **is** a native partial unique index (strictly stronger than the trigger-based alternative first considered); the existing session revoke reasons and `auth_events` vocabulary were not needed by RBAC-A and remain to be confirmed by the phase that first writes them. *(Since `0010`, §20, `scope` is the `StaffScope` set, which adds `grocery`.)*

- **`user_roles`.** The closed `role` set (`VARCHAR + CHECK`, today `('admin')`) gains `moderator`. `admin` keeps its value and means Super Admin; existing rows are untouched. `granted_by` / `granted_at` already record who granted a role and when.
- **`staff_scope_assignments` (new).** `user_id`; a constant `role = 'moderator'` with a composite foreign key `(user_id, role) → user_roles` `ON DELETE CASCADE` (the same constant-column pattern as `business_profiles.kind` — a scope cannot exist without the Moderator role, and removing the role removes its scopes); `scope` (`VARCHAR + CHECK`, the six names of `AUTH_RBAC.md` §27.3, equal to the `CategoryModule` values); `granted_by → users` (`SET NULL`, as `user_roles.granted_by`); `granted_at`; primary key `(user_id, scope)` (no duplicate assignment); an index on `scope`. A row exists **iff** the scope is active — a revoke deletes the row, and the history of grants lives in the staff audit below — so "is this scope granted" is one existence check with no soft-delete predicate to forget. A `news` row is refused by the service until a News administration API exists. **Mutual exclusivity** (`AUTH_RBAC.md` §27.2): a scope row cannot exist without the `moderator` role (the composite foreign key guarantees it), and an account holding `admin` must not also hold `moderator` — a transactional rule of the shared authority service (appointing a Super Admin as Moderator is refused; promotion removes the `moderator` role and, by cascade, its scopes in the same transaction). The database backstop for the exclusivity rule **was built in RBAC-A** as the native partial unique index `uq_user_roles_one_staff_role` on `user_roles(user_id) WHERE role IN ('admin', 'moderator')`, which enforces it under every transaction isolation level.
- **Durable staff audit (new, append-only; the infrastructure is created by the RBAC-A migration and its first records are written by RBAC-B and RBAC-C for their own features — RBAC-G expands coverage, it does not introduce the first writer).** One table for the events of `AUTH_RBAC.md` §27.11: `occurred_at` (the wall clock of the write, like the history tables), `actor_user_id` (null for an operator-CLI action) and a marker for web versus CLI, a closed `action` set (`VARCHAR + CHECK`), `target_user_id`, `resource_type` / `resource_id` (no foreign key: the resource may be a listing, a category or a user), `before` / `after` (JSON objects restricted to an allow-list of keys), `reason`, `request_id`. It never stores a password, hash, token, cookie or OAuth credential. It has no application update or delete path, is not touched by `auth_maintenance purge`, and a trigger-level guard against `UPDATE` / `DELETE` is proposed as defence in depth. It is separate from `auth_events` (the account timeline, purged after 400 days) and from `listing_status_history` (which keeps owning listing decisions).
- **`listing_status_history.actor_role`** (`owner | admin`, `CHECK`) gains `moderator`; existing rows are untouched.
- **Expected to need no change (RBAC-A did not touch them; the phase that first writes the events confirms it — `AUTH_RBAC.md` §27.17, item 4):** `users`, `auth_sessions` (the existing revoke reasons `role_change`, `suspended` and `admin_action` cover the planned revocations) and the `auth_events` vocabulary (`role_granted` / `role_revoked` are reused).
- **Last-Super-Admin invariant:** a service-level transactional rule under a transaction-scoped advisory lock (`AUTH_RBAC.md` §27.6), **not** a `CHECK` — zero Super Admins is a legitimate state before bootstrap. It evaluates _usable_ Super Admins (status `active`, verified e-mail, holding `admin`, a valid usable sign-in method and, once staff MFA ships, an enrolled MFA factor), not merely `admin` rows. "At most 2 Super Admins" is **not** a database constraint (§27.6). This follows the repository's stance on cross-row invariants (service-level; a deferred constraint trigger only for a rule proven repeatedly violated — `DECISIONS.md`).
- **Provider ownership:** how a portal-managed provider resource is represented was **intentionally not decided here**; only the invariant was frozen (`AUTH_RBAC.md` §27.9). **Decided and built in RBAC-D (§18 below): `owner_id IS NULL`, enforced by a CHECK, provenance in the audit.**
- **Not proposed:** per-section or per-role tables (`tutor_admin` and similar), a lookup table for scopes (it would duplicate the code-defined modules) and soft-deleted assignment rows.

## 18. Portal-managed Providers — **`0008` implemented in RBAC-D**

**Status.** Built (RBAC-D, migration `0008_provider_portal_managed`). The product decision is frozen in [`AUTH_RBAC.md`](AUTH_RBAC.md) §27.9; what was built and why is its §31.

**A Service / Professional (`kind = 'provider'`) listing is portal-managed: it has no personal owner.** The representation is `listings.owner_id IS NULL`:

- **No column changes.** `owner_id` was already nullable ("admin-curated / unclaimed content") and the seeded demo providers have always been ownerless. `0008` adds one constraint, `ck_listings_provider_has_no_owner` (`kind <> 'provider' OR owner_id IS NULL`), declared in the model as well so `alembic check` is clean. It is deliberately **one-directional**: `owner_id IS NULL` stays legal for every other kind (the seeds create ownerless businesses), and "an owner is required for a user-created Business / Tutor / Property" remains a write-service rule, not a constraint.
- **Backfill.** `UPDATE listings SET owner_id = NULL WHERE kind = 'provider'`, run before the constraint is added. Nothing else changes: not `revision`, `status`, `submitted_at`, `updated_at`, the search document or any history row. The previous owner survives only where it was always written down — as the actor (`actor_role = 'owner'`) of the Provider's first `submitted` `listing_status_history` row. No staff audit is invented for a past that had none.
- **Provenance is not a column.** Who authored or changed a Provider is in the append-only `staff_audit_events` (`provider_created` / `provider_updated` / `provider_archived`; actor, session, listing id; allow-listed `before` / `after`) and in `listing_status_history` (`actor_user_id` plus `actor_role` `admin` / `moderator`). Neither is ever updated, and neither depends on the author still being staff, so removing or demoting them orphans nothing. A new `created_by` / `managed_by` column was rejected: it would be a second thing to keep consistent with the audit and a tempting place to authorize from.
- **Consequences.** A Provider appears in no owner dashboard, per-status count or quota; a service request for it is a portal request (no stored recipient: the provider side is derived from the target listing's KIND and handled by a Super Admin or a `services` Moderator, `AUTH_RBAC.md` §31); the staff queue shows it with no submitter.
- **Rollback.** `downgrade` REFUSES while a live (non-archived) Provider exists, changing nothing and naming the count (the destructive-downgrade convention of `0007`): a schema rolled back to RBAC-C would leave ownerless Providers that nobody can edit or archive (its write path finds listings through `owner_id`), and no owner is fabricated nor admin assigned to hide that. Roll the application back WITHOUT downgrading (RBAC-C code runs against a `0008` database) or archive the Providers first; with none live it drops the constraint only. Re-upgrading is idempotent (the backfill clears any provider given an owner meanwhile). The CHECK stays one-directional because ownerless non-Provider rows are a documented admin-curated / unclaimed state (§4, §12) that a migration cannot give owners (`AUTH_RBAC.md` §31).
- **Unchanged:** every other table, the `ListingKind` / `ListingStatus` / `HistoryAction` / `ActorRole` vocabularies and the staff audit's closed action set (the `provider_*` actions were reserved by `0007`; `moderation_self_override` stays in the vocabulary, unused).

## 19. Listing contact numbers — **`0009` implemented in Listing Contact v1**

**What a listing holds.** `listings.contact_phone` and `listings.whatsapp_phone` (`varchar(20)`, both NULLable): the number **customers** should use for **that listing**, plus an optional WhatsApp number. Shared by every kind, like the location block.

**Listing data, never account data.** There is **no account-level phone number anywhere in this schema** — `users` holds `email`, `email_verified_at`, `display_name`, `password_hash`, `status`, `last_login_at`; `professional_profiles` holds `user_id`, `plan_code` and timestamps. Nothing copies a number into a listing, because there is nothing to copy from: the only two phone columns in the database are the two above (a test asserts exactly that). A listing's number is typed by its owner, for that listing.

**Public detail only, omitted from search/Saved/bulk summaries.** The owner types these numbers so customers can reach them directly from the listing detail page. Contact numbers are exposed strictly on the public detail read (`GET /listings/{id}`) via `BusinessDetailRead`, `TutorDetailRead`, and `PropertyDetailRead`. Public search hits (`GET /search`), Saved collections (`GET /saved`), suggestions, and all public bulk/summary responses omit both `contact_phone` and `whatsapp_phone` via distinct summary schemas (`BusinessRead`, `TutorRead`, `PropertyRead`). Cards and summaries do not depend on contact fields. Owner private reads and Admin/Moderator review reads retain both fields where appropriate. They are **not** in `search_document` (a phone number is not a search key), so `0009` needed no reindex and search behaviour is unchanged. Provider exposes neither field (portal-managed, Request Service only). Per-listing contact supersedes the old ProfessionalProfile/private-contact plan; Inquiry is deferred.

**Which kinds.** Business (General and Food), Tutor, Property. A **Provider has neither**: it is portal-managed (RBAC-D, §18), its staff API has no contact field, and its columns stay NULL. No constraint was added to forbid a Provider number, deliberately — that would prejudge whether the portal gets its own number in a later phase.

**Canonical shape.** Stored as **E.164** (`+923001234567`) and nothing else, by the one parser `app/core/phone.py`. Two row-local CHECKs enforce it as a backstop: `ck_listings_contact_phone_e164` and `ck_listings_whatsapp_phone_e164` (`<column> IS NULL OR <column> ~ '^\+[1-9][0-9]{7,14}$'`), both declared in the model so `alembic check` is clean. A path that forgot to normalise is refused by the database rather than storing `0300 123 4567`.

**Requiredness is a write rule, not a database rule** — the same decision the location block made for "a Property needs a map pin" (`LOCATION_MAP.md` §3.1), and for the same reason: rows that existed before the field have none, so a `NOT NULL` (or a `kind`-aware CHECK) would make them impossible to migrate and would re-check on every `UPDATE`, blocking approve / reject / archive of a legacy row. `listing_state._validate_contact` requires `contact_phone` for Business / Tutor / Property on every owner create **and every owner edit**; moderation and archiving never validate it. A validated database rule may be added by a later migration once a drift query (owner-managed rows with `contact_phone IS NULL`) returns zero everywhere.

**Migration `0009` is additive and guesses nothing.** Two `ADD COLUMN`s (no default, no generation, so no table rewrite) and the two CHECKs. **No data statement**: no backfill, no number parsed out of a description, nothing copied. Existing rows become the documented legacy state by construction — both columns NULL, every other column untouched (`status`, `revision`, `submitted_at`, `updated_at`, `search_document`).

**Rollback.** `downgrade` drops the two CHECKs and the two columns, and with them the numbers owners typed. It does **not** use the refusing-downgrade convention of `0007` / `0008`: those refuse because the older release would be left unable to manage live rows (an ownerless Provider nobody can edit) or would destroy an append-only audit. Here the older release simply has no contact concept — every row stays valid, editable and moderatable without these columns — so dropping them is a clean, complete reversal of an additive change, exactly as `0005` does for the location block. Re-upgrading invents nothing: the numbers are gone with the column that held them.

**Unchanged:** every other table, every vocabulary, the search index and document composition, ownership, quota, the listing state machine and the moderation rules.

- **Delivery attempts have no table:** they are read from the status history (each move to `out_for_delivery` begins one; the next move out decides it).
- The order's `cancel_reason` stays the **customer's** field; a staff reason lives in the history row.
- Not created: quotation, supplier, bill, price-per-line, inventory, refund or issue-resolution tables.
- **Downgrade** locks the six tables and **refuses, changing nothing**, while any order is past `submitted`/`cancelled`, is assigned or priced, or any agreement, payment, event, staff history row or changed value cap exists (`DEPLOYMENT.md` §17).

## 23. Staff revision — **`0013` implemented in GROCERY-4A** (not applied to any real database)

**Additive: one column, no data statement.**

| Table | Change | Rules the database enforces |
|---|---|---|
| `users` | adds `staff_revision INTEGER NOT NULL DEFAULT 0` | `ck_users_staff_revision_non_negative` |

- It counts the changes to the account's staff role and scopes and is **on the account**, so it survives removal and re-appointment. The application only ever adds to it (`StaffAuthorityService`, under the account's row lock, in the transaction of the change).
